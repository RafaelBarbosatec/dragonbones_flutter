Both packages are published on pub.dev:

| Package | Version |
| --- | --- |
| [`dragonbones`](https://pub.dev/packages/dragonbones) | 0.1.0 |
| [`dragonbones_flutter`](https://pub.dev/packages/dragonbones_flutter) | 0.1.0 |

A pub.dev release cannot be deleted — only retracted — so the trigger is always a
human decision, never a CI side effect. This page is the release sequence for the
next version.

Check the current state at any time:

```bash
cd packages/dragonbones          && dart pub publish --dry-run
cd packages/dragonbones_flutter  && flutter pub publish --dry-run
```

<Info>
  This repository is named after the renderer package because that is the one
  users import, but it hosts **both** packages: `dragonbones` (the runtime, in
  `packages/dragonbones`) and `dragonbones_flutter` (the renderer, in
  `packages/dragonbones_flutter`). The two are published to pub.dev as separate
  packages.
</Info>

## Why the order matters

`dragonbones_flutter` depends on `dragonbones` through a **version range**:

```yaml
dependencies:
  dragonbones: ^0.1.0
```

That is exactly why the runtime has to go out first: until the new `dragonbones`
version is on pub.dev, pub cannot resolve the renderer's dependency. Publish the
runtime, let the pub.dev index catch up, then publish the renderer.

<Warning>
  A consequence worth planning for: there is a window between step 1 and step 2
  where the runtime is public and the renderer is not. If the runtime goes out
  with a bug, it is public (retractable, not deletable). Dry-run the renderer
  locally with the new range *after* step 1, before running step 2.
</Warning>

## Steps

```bash
# 1. runtime first
cd packages/dragonbones
#    - bump `version:` in pubspec.yaml
#    - add the new version to CHANGELOG.md
dart pub publish --dry-run     # must be clean before the real thing
dart pub publish               # <- irreversible

# 2. then the renderer
cd ../dragonbones_flutter
#    - bump `version:` and add it to CHANGELOG.md
#    - raise the dependency on the new runtime:
#         dragonbones: ^0.2.0
flutter pub get && flutter test
flutter pub publish --dry-run
flutter pub publish
```

## Name availability

`dragonbones` and `dragonbones_flutter` are the names this project publishes
under. `dragonbones_dart` and `dragonbones_canvas` were also free when last
checked and remain reasonable fallbacks — the runtime and the renderer can be
named independently.

## What is deliberately not in the archive

`packages/dragonbones/.pubignore` drops the `tool/` directory. Those scripts
(`check_against_oracle.dart`, `parse_check.dart`, `inspect_fixture.dart`) read the
reference dumps and fixtures from the repository root, which is outside the
package — shipping them would ship something that cannot run. They live in the
repository, where they work.

## Before a 1.0

Not blockers for a first release, but worth knowing. See
[Limitations](/limitations) for the full, specific list:

- **Animation events** (`EventObject`) are not ported — the highest-value gap.
- **Animated IK**, **`SlotZIndex`**, **`SlotAlpha` / `BoneAlpha`**, **path
  constraints** and **`Surface` bones** are parsed but not evaluated. No asset in
  the 51-asset test set needs them; a project that does would hit a wall.
- **Appearance is only eyeballed.** CI proves pixels are produced, not that the
  result looks right.
- **No benchmarks.** Pooling was dropped, so allocation behaviour differs from
  upstream and is unmeasured.
- The example app is a demo, not documentation.
